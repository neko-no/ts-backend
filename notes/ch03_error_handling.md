エラーでも回復可能なものと不可能で実行を止めないといけないものがある。

- 回復可能なもの　エラーを戻り値として扱うこと
- 回復不可能なもの　例外による伝播を行い、処理を止める



## 例外（`throw`）ではなく戻り値（`Result`）でエラーを扱う理由



例外での課題

- 例外の処理の保証をする機能がない
- エラーの内容を合成できない
- 制御フローが中断するので、デバックなどが難しくなる



関数型プログラミングでの対応

- エラーを関数の戻り値として扱う
  - 関数シグネチャにエラーの内容が現れる　Unionでエラー時の型が絞り込める
  - 静的解析時に検査できる
  - テストのしやすさが向上する



Resultを適応すべき範囲

- 呼び出し元で分岐をさせるかで決める
- 色々なところで処理するよりも、境界で一律に変換するのが効率的

　

- ## node.jsのassertを使って機能を実装している



契約

- 契約による設計で説明されているもの
  - 事前条件　実行前に満たすべき条件　→ 呼び出す側が満たすもの。提供側でassertによって、表明する
  - 事後条件　実行後に満たすべき条件　→ 提供側が満たす。提供側でassertによって表明
  - 不変条件　各操作を通じて維持されるべき条件

## TypeScript の基礎メモ（Result の定義を読むために確認したこと）

関数シグネチャ

- 関数の「外から見える型の取り決め」。引数の型・戻り値の型・関数名で、実装は含まない
- `Result<T, E>` を戻り値にすると、成功時の型 `T` と、失敗時の型 `E` がシグネチャに現れる
  - 例外は `throw` がシグネチャに現れず、`try/catch` を忘れてもコンパイルが通る

判別可能なユニオン型（`Ok<T> | Err<E>`）

- `|`（ユニオン）は「AまたはB」。`&`（交差）は「AかつB」で別物。`Result` は「どちらか」なのでユニオン
- `ok` が `true` / `false` の目印（判別プロパティ）になり、`if (result.ok)` で型が絞り込まれる（ナローイング）
  - 確認前に `data` / `error` を読むと型エラーになる → 失敗の処理を飛ばせない
- 型が保証するのは「処理を書かない状態を許さない」まで。失敗時にどう処理するかは利用側が決める

ジェネリクス `<T>`

- 型の入れ物。呼ばれたときに型が決まり、引数の値から推論される
- アロー関数は `()` の直前、通常の関数宣言は関数名の直後に書く
- オブジェクトを返す短い書き方は `=> ({ ... })`。`=> { ... }` だと関数本体のブロックとして読まれる

型引数の制約 `S extends boolean` / `S extends string`

- ここでの `extends` は「〜の仲間である（代入できる）」。`interface A extends B` の拡張とは別
- 親（`ResultLike` / `ApplicationError`）は「共通の形」を決め、子が `true` / `false` や文字列リテラルを渡して 1 点に絞る
- `kind: string` のままだとエラーの種類が型に残らず、`switch (error.kind)` での絞り込みや網羅性チェックが成り立たない

`interface` / `type` / `const`

- `interface` と `type` は型の世界（実行時には残らない）。`const` は値の世界（実行時に残る）
- 型と値は別の名前空間なので、同じ名前を付けられる（コンパニオンオブジェクト）
- 関数 `Ok(...)` が返すのは「`Ok<T>` という型の形をした値」。関数が型を返しているわけではない

`const` とリテラル型・`typeof`

- `const kind = 'X'` の型は `string` ではなく、`'X'` だけを表すリテラル型。`let` だと `string` に広がる
- `<...>` に入れられるのは型。値の `kind` はそのまま書けず、型の位置の `typeof kind` で型を取り出す
- 値と型で同じ文字列を二重に書かずに済み、値を変えると型も追従する

`export`

- `export const X` だけだと、同名の `interface X` は export されず、型としては使えない
- 末尾の `export { X }` は、同じ名前の型と値を両方 export する
