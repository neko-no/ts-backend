データと振る舞い



## OOP



データと振る舞いを分離することによる利点

- 予測可能性　隠れた状態遷移への依存の抑制をする
- テスト容易性　関数単体での検証が行える
- 再利用性　互換性があるデータに対しては、適応ができる
- 変更容易性　影響範囲の局所化



どれも設計で目指すべき方針として、様々な書籍で言われていたことである。



クラスにおける課題

- 振る舞いとデータが一体で設計される
  - 機能が増えると、クラス間の関係を追うのが難しくなる。
  - 呼び出しや状態遷移の考慮が追いづらい
  - 対策もできるが、設計方針をチーム全員で合意するのは結構コストがかかる
- カプセル化が、クラス同士を複雑にする要因になり得る
  - 依存しているクラスのメソッドを前提にしていると、関係性の把握がしづらい
- BEにおいて、状態をもつケースがそもそも少ない。

## DOP



データ指向プログラミング

- データと操作するコードを分ける
- 関数型プログラミングの方針　不変データと純粋関数



TSとDOPとの親和性

- 構造的型付け　構造が一緒であれば、関数を再利用できる。(だから第1章で変性の話をしたのか。)



何が良いのか？

- 不変なデータ　readonly制約によって、変更を不可にできる
- 純粋関数　副作用持たないので状態がわかりやすい
- 関数のモジュール化　過度な分離をせず、凝集性を高めている



書籍の例では、判断する部分とデータの中身を変更したい場合に分かれている。データの中身を変更したい場合は、値を取り出して、新しいオブジェクトとして返却する。

コンパニオンオブジェクトによるモジュール設計

- コンパニオンオブジェクト　型と同じ名前のオブジェクトを定義し、1つの名前のもとで公開する
- 型とファクリトリー関数を一括公開できる



型と値が同じ名前で共存できる理由

- 型と値は、別々のグループ（置き場）に登録されるため、同じ名前でも衝突しない
  - interface / type → 型のグループだけ
  - const / function → 値のグループだけ
  - class / enum → 型と値の両方
- 使われる場所で、どちらを指すかが決まる
  - `const p: Period` の `Period` は型
  - `Period.build(...)` の `Period` は値（オブジェクト）
  - `typeof Period` は、値の型を取り出す
- `export { Period }` で、型と値の両方がまとめて公開される。`import { Period }` の1回で両方使える
- 同名にできるのは、型と値の組み合わせだけ。`const` と `const` のように同じグループで重複するとエラー
- 型は実行時に残らない（型消去）ので、実行時に衝突することもない
- classは、型と値の両方を作るので、最初から同じ名前で使える
